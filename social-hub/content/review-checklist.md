# Review and publishing checklist

Keep this with every draft. Owner reviews and publishes manually; this project does not publish to external accounts automatically.

## Before writing

- [ ] Confirm the post’s audience and one useful takeaway.
- [ ] Verify every product detail against the current product/repository state.
- [ ] If a screenshot or workflow is illustrative, label it clearly as a concept.
- [ ] Check current platform rules if the post explains WhatsApp messaging, templates, consent, or APIs.

## Before approval

- [ ] No unsupported customer outcomes, metrics, partner/certification/provider claims, guarantees, or unfinished features described as live.
- [ ] No copied competitor phrasing, layouts, visual identity, screenshots, or customer story.
- [ ] Palette contains only `#16A34A`, `#059669`, `#0F172A`, `#ECFDF5`, `#F3F4F6`, `#FFFFFF`; typography is Inter.
- [ ] Check contrast and mobile legibility; meaningful text is not conveyed by color alone.
- [ ] Add alt text/captions; captions are readable and do not rely on sound.
- [ ] CTA points to a working destination. The project setup notes say `okaychat.in` was unresolved when checked; verify before using it.
- [ ] Hashtags are relevant and limited; verify platform conventions before posting.
- [ ] Date, channel, asset filename, reviewer, approval status, and final URL are recorded.

## Publishing log fields

`Draft date | planned post date | channel | format | asset | reviewer | status | final URL | notes`

Statuses: `Draft — owner review required` → `Approved by owner` → `Published by owner` or `Needs revision`.

## Weekly review

- [ ] Note saves, meaningful replies, profile visits, and qualified enquiries where available.
- [ ] Compare like formats over time; do not treat a single post as proof.
- [ ] Capture audience questions as future topics.
- [ ] Refresh product-claim checks and update the calendar when build status changes.
